# Assistance API Contract Review

**Status:** Design review only; the API is specified but not implemented or deployed.

## Findings to resolve before a backend implementation

### 1. Authentication and authorization must be enforced by the server
The OpenAPI file declares bearer authentication, but documentation alone does not enforce it. The future service must validate token issuer, audience, signature, expiry, and relevant roles/scopes. Never trust a role or reviewer ID supplied by the client.

### 2. Synthetic-only is not a substitute for privacy controls
The current `demoRecord: true` constraint is useful for the prototype contract, but a production API should have a separate environment/configuration policy. Do not use a client-provided boolean as the only barrier against real data. The server must be configured to reject real records in demo environments.

### 3. Review history should be append-only
A review operation should record the authenticated actor, timestamp generated by the server, prior state, new state, and a correlation/request ID. A caller must not choose `reviewerId` or `reviewedAt`. Do not store unnecessary sensitive details in free-text notes.

### 4. Idempotency and concurrency
Creating applications and recording reviews may be retried after network failures. Before a real backend is used, define idempotency behavior and enforce state transitions atomically. Duplicate retries must not create duplicate records or reviews.

### 5. Pagination and data minimization
The list endpoint must apply authorization filters before pagination and must not expose fields outside the caller's role. Use stable ordering and bounded page sizes. Do not provide broad cross-institution search by default.

### 6. Error handling
Use consistent structured errors, but avoid revealing whether a protected record exists to an unauthorized caller. Keep stack traces and internal service details out of client responses.

### 7. OpenAPI syntax validation
The specification should be parsed by a standards-compliant OpenAPI validator in CI. The existing Python contract tests check selected strings; they do not prove the document is valid OpenAPI or that any endpoint works.

## Required next implementation gate

- [ ] Add OpenAPI syntax validation to CI using a pinned, maintained validator.
- [ ] Decide on a minimal backend framework only after reviewing project constraints.
- [ ] Add server-side schema validation and role enforcement tests.
- [ ] Add append-only review audit events.
- [ ] Add concurrency and idempotency tests for state-changing operations.
- [ ] Keep all automated tests synthetic-only.
- [ ] Verify the latest CI run and report its actual result.
- [ ] Do not connect to OpenG2P, Keycloak, X-Road, payment rails, or real SFD data until the narrow local workflow is implemented and reviewed.

## Acceptance boundary

A passing specification-validation job means only that the API document parses. It does **not** prove backend correctness, security, compliance, operational readiness, or production suitability.
